## Findings
1. LOW (dev/test only) `src/components/search/ResultCard.tsx:12-16` with `src/lib/search/search.ts:profilePhotoUrl`: in MOCK mode, if `NEXT_PUBLIC_SUPABASE_URL` is set (a developer's `.env.local`), the page asks the real project's public storage for the made-up photo paths. Nothing is sent but the request, and it 404s, but the MOCK run is then not offline and the visitor's IP reaches the hosted project. CI has no URL, so unaffected. The builder's own mock spec does not block these requests (mine does). Suggested fix: skip the photo URL when `isMockEnabled()`.
2. LOW `src/lib/mocks/mock-search.ts:301`: `decodeURIComponent` on the id throws `URIError` for a malformed escape (`/api/chefs/%E0%A4%A`); the real route gives the normal 404. Matters for T-041 (hand-edited URL). Pinned with an `it.fails` in `mock-search-tester.test.ts`; when fixed, change it to `it`. Suggested fix: try/catch and return `NOT_FOUND()`.
3. INFO `src/lib/search/search.ts:buildPins`: a city that has exactly one postal area would put the pin on that chef's own service area centre. The real seed has no such city (minimum 4). If areas are ever added or removed so a city has one, the "never a chef's area" claim in the page text no longer holds; worth a note in the contract.
4. INFO `src/components/forms.tsx:79-95`: `SubmitButton` uses `disabled` while busy, so a mouse or keyboard user who just activated "Find chefs" loses focus until the result moves it; focus is then set (heading or alert) so nothing is stranded. Other forms use the same component.
5. INFO `src/components/search/SearchView.tsx` empty `FormAlert` (role alert, sr-only) is always in the DOM, so a test or screen reader sees two alerts with the Next route announcer; harmless, noted because tests must filter by text.
6. INFO `src/lib/mocks/mock-search.ts`: the mock date filter uses made-up weekdays (documented) and the offset cursor `m<number>` (documented); all other behaviour is the real pure functions, so parity is by construction. Verified by the 22 mock tests above.

No bugs sent back to the builder as blocking. Findings 1 and 2 are small fixes the builder may take in one batch with review notes.
