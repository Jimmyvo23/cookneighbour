## Findings (none is a security or privacy leak)
1. MEDIUM, confirmed, known. `src/lib/booking/changes.ts:311` (`CONTACT_RULE` ends "Chat stays open.") is reused by `contactOpenText` (:330) and `CONTACT_ENDED_TEXT` (:339). On `no_show_customer` and `no_show_chef` the chat is hidden (D-94) but both pages say "Chat stays open.": in the open window (`data-testid=contact-window`, up to 7 days after the last day) and after it (`contact-later`), on `BookingDetailView.tsx:380` and `ChefBookingView.tsx:589`. Proved by 8 `it.fails` in `ChatContactText.tester.test.tsx`. All other statuses are honest: accepted and completed (chat open) say it; cancelled (`CONTACT_LOCKED_TEXT`), declined, expired (kind `never`, no text) and requested (no window text) do not. The builder is right to leave it out of `CONTACT_LOCKED_TEXT`. Minor: an accepted/completed booking that is frozen says "stays open" while the chat is read only (not counted as false). Suggested fix: pass the status in, so the sentence is only added when the chat shows. This is a "false promise in the UI" (lessons-learned section 3); Planner/Jimmy decide whether it blocks the merge.
2. LOW-MEDIUM. `ChatSection.tsx` Bubble (about :330): "Retry sending" shows for a retryable failed bubble even when `frozen` turns true (read only). It would POST; the server answers 409 `frozen`, so nothing is saved, but the acceptance wording "no request that could send" is not met. A frozen booking with a bubble that failed earlier needs the page to receive `frozen=true` later; in the builder's own 409 path Retry is already removed. `it.fails` in `ChatSection.tester.test.tsx` ("a failed message's Retry goes away when the booking becomes frozen"). Fix: hide Retry when `readOnly`.
3. LOW (a11y). `useChat.ts` (`setAnnouncement`): two identical messages from the other party in a row ("ok", "ok") give the same string, so the live region does not change and a screen reader reads only the first. `it.fails` with a MutationObserver. Fix: include a counter or clear the region first.
4. LOW. `src/components/booking/testkit.tsx` fallback: the condition `!init?.method` is never true because `apiFetch` always sends `method: "GET"`, so an unrouted messages GET still answers 404 ("no route"), not an empty page as the comment says. Harmless (existing page tests pass), but the comment is wrong and the branch is dead. `it.fails` documents it. It does not weaken any check.
5. NOTE. After a reconnect the reload shows messages that arrived while paused but does not announce them. I did not assert this; the contract does not say. Mention to Jimmy only if he wants it.
