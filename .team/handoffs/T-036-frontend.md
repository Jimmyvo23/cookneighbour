## Lessons-learned section 3 self-check
IDs come from the loaded list or the URL and are re-checked by the server (404 for unknown); reviewed paths and address are echoed from the loaded application; approve and decisions are one server call each; reasons use the shared rule before sending and again on the server; every check status has a MOCK badge; UI text about files and approval matches behaviour (approve does not turn on chef's home; the chef's own `missing` list does not check files); focus goes to the error; server guard on /admin.

## Known gaps or risks
- Q-16 (open, Jimmy): the UI does not hide or warn about the builder defaults. An admin can set a check back to `not_started` or `pending`, set an approved chef's check to `failed` (status unchanged), review a pending or rejected chef's kitchen, and rejecting leaves chef's home on. The "Checks pending" filter ignores the police check; its label says ID, food handler or kitchen. Suggested UI follow-up once Q-16 is decided: flag an approved chef whose check is `failed`.
- The review page has no "next chef" shortcut, no search by name, and no `submittedAt` (the list shows when the chef signed up; the backend has no submit time).
- The food-handler file may be a PDF: it is offered as a link, not previewed. Images are shown with a plain `<img>` (signed link to private storage).
- A hidden earlier page stays mounted after in-app navigation, so tests must scope to what is visible (`filter({ visible: true })`).
- `npm run build` prints one `api: unhandled error ... cookies() rejects ... route "/api/admin/chefs"` line while prerendering (the GET list handler is tried as static). It is the T-035 route, harmless to the build (the route stays dynamic), and not touched here; Backend may want `await connection()` or similar. The other GET routes do not log it.
- Real-route specs ran in CI only (no Docker locally).
