Findings
- LOW src/components/booking/PickupSections.tsx:114 and :433. Once the booking leaves `accepted` (for example completed), the whole pickup section returns null unless a day has proposal history. A customer who confirmed without ever proposing a time (allowed) then loses the "Picked up on ..." record on both sides. Suggest a follow-up: also render when any day has `pickedUpAt` (`hasHistory || b.days.some(d => d.pickedUpAt)`).
- LOW (Tester note 1, stale page) src/components/booking/PickupSections.tsx:529 (MissedPickup) and the `ConfirmPickup` error path. After a stale 409 (`pickup_confirmed` for the chef, or `wrong_status` for the customer after the chef marked missed) the alert text is correct and focused, but the page isn't refetched, so the dead action stays until a reload. This is the same pattern as the other change sections (no refetch-on-409 anywhere yet), so it's not a blocker for this PR. I recommend one shared follow-up: on 409 INVALID_STATE, refetch the booking after showing the alert, keeping focus on the alert.
- NIT src/components/booking/PickupSections.tsx:132 and :451. The intro paragraphs still describe only "propose a time / accept or decline". One clause such as "or tell the chef you picked up the meals" (customer) / "or the customer confirms they picked up" (chef) would make the new button discoverable.
- NIT src/lib/api/types.ts:656. The `PickupProposalView.status` doc says `void` = "the booking ended ... before an answer". It now also means "closed because the customer confirmed the pickup". Update the comment.
- NIT src/lib/mocks/mock-booking-changes.ts:822. When voiding, the mock overwrites `respondedAt` with now. The server keeps the existing value (`coalesce(responded_at, now())`), so an accepted proposal keeps its original answer time. Use `p.respondedAt ?? now.toISOString()`.
- NIT src/lib/mocks/mock-booking-changes.ts:131-132, :216-219. The `SeedOptions.days[].pickedUp` option is never used (the hook path at :393-402 does the work). Remove it or use it.
- INFO src/components/booking/PickupSections.tsx:309. "The chef is told" is true on the server (one `pickup_confirmed` notification, migration line 239) and on the chef's booking page, but the notification isn't shown in the UI until T-047. That's acceptable, just noting it.
- INFO (Backend, for PR #145, not this PR) supabase/migrations/20261018100000_pickup_confirm.sql:246. `pickup_propose` doesn't refuse a confirmed day, so a direct API call can still propose a time after "picked up". The frontend hides the form, so there's no UI path to it. Backend should decide whether to add a `pickup_confirmed` refusal there.
